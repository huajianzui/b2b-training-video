# 场景编写提示词

用途：按用户确认过的功能清单，探查真实页面，写出演示脚本的场景（旁白 + 操作 + 断言），并演练到全部通过。
占位符：`{{module}}` 模块名、`{{features}}` 功能清单文件、`{{featureIds}}` 本次要写的功能 id、`{{script}}` 要写入的脚本文件（已有配置，只缺 scenes）、`{{recorder}}` 工具目录（Skill 用法下即工作区的 `.training-video/`）、`{{auth}}` 登录态文件、`{{data}}` 演示数据说明。

---

你在为「B 端系统培训视频自动生成工具」写演示脚本。脚本里每个场景有一段中文旁白和一组页面操作：工具先把旁白合成配音，再用 Playwright 照着操作真实系统录屏，旁白念到哪、操作做到哪；同时生成带截图的 Word 操作手册。观众是第一次用这个系统的业务人员。

## 输入

- 模块：{{module}}
- 功能清单：{{features}}（用户已确认；每个功能的 how / when / requires 是你写场景的依据）
- 本次要写的功能：{{featureIds}}
- 演示数据：{{data}}
- 脚本格式：`{{recorder}}/script.js` 文件开头的注释；通用示例 `{{recorder}}/script.yaml`；Element Plus 控件的处理见 `{{recorder}}/adapters/element-plus.js` 开头注释

## 工作方式

1. **先看页面再写（同会话批量快照）。** 用页面快照工具探查：`node tools/snap.js {{auth}} <步骤文件.json>`（用法见 `tools/snap.js` 开头注释）。需要探查多个独立页面时，优先在单个步骤文件中使用 `["parallel", [["list", "http://.../list"], ["detail", "http://.../detail"]]]` 同会话多标签页并行抓取，不要每看一页冷启动一次浏览器。它保存截图和无障碍结构（`output/_snap/*.aria.yaml`），定位要以无障碍结构里真实的角色和名称为准，不要凭代码猜。步骤文件放在 `output/steps/`。
2. **写场景**，追加到 {{script}} 的 scenes 下。
3. **快速演练与旁白预热**：
   - 先校验 `node script.js {{script}} --rehearsal`，只对未验证或已变更的操作安排演练。
   - 调试或修复单个场景时，使用 `node play.js {{script}} --dry --scenes <范围>` 只跑失败/新增的接续组（工具补齐接续组；它与 `--shots` 互斥、**不能替代 `produce` 的 check 环节**），同时可在后台并行跑 `py -3 tts.py` 预热 `output/tts-cache`。
   - 演练按 `rehearsalMode` 走，提交分支不执行；要验证提交分支用 `node play.js {{script}} --dry --trial`（动作照常跑，写请求被拦截、不落库，`produce` 录制前会自动跑一次）。
   - 全量演练优先运行 `node produce.js {{script}} --dry`（生成 `check` 记录与演练手册），通过后直接用 `node produce.js {{script}} --from tts` 进入正式录制，避免重复跑第二遍全量演练。实际写入必须等待本轮人工确认，页面信号会自动继续，不要求用户再回消息。
4. 失败时保留 `output/run-report.json` 和必要现场，先查明原因/当前数据状态。按准备单的阻塞策略停止、跳过依赖功能或补充文字讲解；没有新证据不盲重试，不通过取消勾选抹掉原批准范围。细则见 `prompts/production-brief.md`。

## 安全

- 这是真实系统。**用快照工具探查时不提交任何数据**：不点保存、确定、确认、提交类按钮。
- 写数据功能在组尾写 ending：演练按 `rehearsalMode`、正式录制按 `writeMode` 分别选择 `ending.submit / ending.cancel`。两轮选择不同则两种都要写；基础 actions 不得保存。任一 submit 都要求用户允许测试数据和已核实的 writeRequests。
- 登录、演练、录制都会拦截未批准写请求；POST 查询和登录须通过明确的 readOnlyRequests 清单。不要通过改清单确认、改执行器、修改安全字段或其他工具绕过错误。接口语义或授权缺失时交回主 Agent 核对。
- 演练提交会改变数据，正式录制前需用户确认已复位或换用独立数据。复位方式与不可逆目标写在准备单里：归档、停用这类状态常不可回滚，新建类操作重录会产生同名重复记录。提交后失败也可能已经写入，先交回用户核对，再重新确认；不自动回滚、清理或反复提交。
- 真实提交时，新建的数据名称统一带「培训演示」前缀，便于识别和清理；不修改、停用、删除已有的业务数据，要演示这类操作就用演示数据说明里指定的专用记录。
- 不要修改 `{{recorder}}` 下除 {{script}} 和 `output/` 以外的文件。

## 场景规则

1. **以「业务总纲（`thesis`）」为灵魂，抓住主要矛盾，主次分明编排（严禁平均用力记流水账）**：
   - **篇幅按主次（`priority`）倾斜**：
     - **`core`（核心主线 / 设计巧思）**：必须占全片 **60%~70% 的篇幅**。每个核心功能必须先讲**「为什么这么设计 / 解决什么业务痛点或防止什么错误（Why）」**，再讲具体操作（How）；复杂交互拆成多个 `continue: true` 的连续场景，把每一处防错巧思、联动计算、前后状态变化完整展示清楚。
     - **`supporting`（支撑性功能）**：围绕主线同一个业务案例顺带串联演示（1 个场景讲清何时使用与结果）。
     - **`routine`（常规外围操作）**：普通筛选、简单启停或外围字段修改，能并入主线开场顺带一提的就合并，或用精炼单场景快速带过，绝不让外围操作稀释主线。
   - **造数与实操必须“把设计演出来”（严禁只为走通流程造平庸数据）**：
     - **正反对比演示设计**：凡系统有保护、分类、分摊或条件差异规则（例如批量操作中的“仅填空白项不覆盖已有值”、编码/单据的“同组归类连号 vs 独立新号”、预算/配置的“共享组动态反算 vs 独立固定项”），必须在画面上同时构造**正反两组对比数据**同屏操作，让观众亲眼看到系统规则在不同数据上的差异化效果。
     - **阈值边界演示设计**：凡系统有额度封顶、比例闭环、冲突协调、版本对照调减（例如 `100%` 比例闭环校验、总额/周期上限封顶与跨单冲突协调），必须构造**真实触发阈值边界的冲突数据**（如先打破平衡触发系统预警/拦截/负差额，再演示用系统的纠偏或协调功能将其调平闭环），严禁填极小值或留 `0%` 空跑过场！
     - **防错纠错演示设计**：凡系统有预校验或前置拦截（如批量预校验、导入预检、表单业务校验），必须先构造一处典型业务异常（如漏填必填项或唯一性冲突），触发前置拦截向观众展示系统如何把错误挡在入库前，再当场修正并重检通过。
   - **保持单向顺畅流转，禁止页面来回折返**：
     - 相关操作用同一个案例衔接，后面场景加 `continue: true` 接着上一个的页面状态（`continue` 三条硬约束：第一个场景不能写；关联的 feature 列表必须与上一场景**完全一致**；上一场景不能有 `ending`）。
     - 由于写请求只能在 `ending.submit` 触发，若同一场景串联两个页面且只在其中一个页面点击保存，必须按**「先讲只读/查看页 → 再进入保存页并在 `ending.submit` 当场保存」**的单向顺序编排，**严禁 `A页 → B页 → 又跳回A页保存`**。
   - **跨角色主线使用 `switchUser` 无感切角**：当一条完整业务主线需要在多个角色间交接时，在场景级配置 `switchUser: <用户名>`，由执行器在录制前预取凭证、在场景切换时毫秒级注入 `cookies/localStorage` 并刷新目标业务页；**严禁在场景 `actions` 中写 `/login` 或 `/admin-login` 填表登录步骤**。
   - **画面洁净与强依赖链全链路闭环**：避免让满屏杂乱的历史垃圾测试数据（如 `test111`）或未脱敏生产数据入镜（`isolated` 隔离库用黄金洁净基线，`shared-test` 共享库用专属容器或筛选聚焦）。存在前后强状态依赖（`dependsOn`）时，在允许写测试数据的环境下两轮均走 `submit` 真实落库跑通全链路。查看带有默认筛选或状态页签的汇总/明细列表时，必须显式切换筛选到当前所讲的业务阶段（如从默认的草稿/初版切换为已发布/终版），确保画面数据与旁白完全一致。
2. **通用操作不单独演示。** 清单里标了 `shared` 且没勾选的功能（查询、翻页、弹窗保存取消等）已在《系统通用操作》里讲过。每类页面的第一个场景用一句话带过，如「页面上方可按项目、业务阶段筛选，查询方法和其他页面相同」；有本模块特有含义的条件（清单 desc 里写了）简要说明含义。不要演示输入、查询、重置的过程。
3. **介绍功能首先要让观众找到功能（必须从菜单逐级点进去，严禁直接 `goto` 跳过菜单）**：
   - 观众看培训视频的第一诉求是**「这个功能在哪个菜单底下、怎么找到它」**。
   - 每个模块或新功能页面的进入场景，**必须从带完整导航栏的首页/工作台开始，在 `actions` 中真实点击展开左侧/顶部一级菜单 → 点击二级/三级菜单项进入列表 → 点击对应状态筛选页签（如「待发布项目」）或操作按钮**，同时旁白必须同步指路（如「首先在左侧菜单展开招标竞价管理，点击竞价采购一次性进入列表，再切换至待发布项目」）。
   - **严禁直接用 `goto` 跳到业务列表子路由，更严禁在含 `iframe` 的门户系统中把内层 `iframe` 的 URL 拎出来单独 `goto`**（单独 `goto` 内层 URL 会导致整个左侧菜单栏和顶部栏消失，观众完全找不到入口！执行器已原生支持自动穿透 `iframe` 定位内层元素，全程保持在主框架下操作即可）。
   - 若模块首页存在多种业务类型卡片或页签（如多类任务库），首幕应先简要说明各类型定位及核心差异，再进入主演示对象。
4. **旁白写给第一次用的人听**：
   - 口语、简洁，一个场景通常 40–90 字；说清楚「在哪、点什么、会发生什么、为什么这么做」。篇幅不足时拆连续场景，不删关键知识或只复述按钮名。
   - 写数据的功能先用半句话讲什么时候用（如「不再使用的订单可以关闭」），再讲怎么操作；有反向操作或限制的顺带一提（如「关闭后还可以重新打开」）。
   - 不要念演示数据的具体名称或编码（说「这一条」「某个订单」），除非观众需要照着输入（如查询关键字）。
   - 按业务顺序通读全篇，用“信息建好后，接着……”等自然过渡；集中审稿和抽听，不逐场景打断用户。
   - 提到界面文字时直接说，不加引号书名号；不念网址、编码规则之类的技术细节，除非对用户有用。
   - **写数据功能必须讲到保存这一步，且正文与收尾严禁重复话术**：
     - 场景最终旁白由正文 `narration` 与收尾 `ending.*.narration` 拼接而成。**正文 `narration` 只负责讲业务背景、规则逻辑、字段含义与填写过程，到填写完毕即止；把「点击保存/提交/确认」及提交后的结果统一放在 `ending.*.narration` 中**，严禁在正文末尾先说一遍“点击保存并提交”、又在 `ending` 里重复说一遍“确认无误后点击保存并提交”（会导致视频里先干念一遍再去操作）。
     - 真实提交（submit）：点保存，断言成功提示或新数据出现，旁白讲结果。
     - 填完取消（cancel）：先讲“核对后点击提交，申请将由……审批，通过后……；暂不发起时，可以取消返回”。核实审批节点和生效条件，未执行结果用条件语气，执行范围记入内部核对，不在旁白念“本次只演示 / 本片段未执行”。取消是可选退出；制作通知开关、测试环境或授权不进入旁白，正常业务通知选项仍应说明。
     - 停用、归档这类有二次确认的操作同理：讲清确认后的结果，再按本阶段的 rehearsalMode / writeMode 确认或取消。
   - 资格限制按已核实的具体业务角色解释谁能办理、何时可用；可展示禁用提示，后续流程有依据时仍要说明。演示账号配置留在内部准备，手册与视频同一口径。
   - **异常也要讲清业务含义**：结合画面说明现象、已核实原因、适用的处理或正常路径、如何验证。区分可纠正的输入错误与一次性操作 / 状态不适用；后者不能靠改编码、清记录绕过，应说明适用范围与后续维护路径。仅有报错不能断定历史原因，证据不足先核实，不编造解释；未执行的后续用条件语气，制作范围只记内部核对。
   - **每个逗号分句控制在 20 字以内**：长句适当用逗号断开，避免超长名词短语导致 TTS 语速失真或字幕折行硬切拆词。
   - **多音字注音铁律（严禁单字通配替换）**：配置 `pronounce` 时，**严禁对「行、重、调、长、还、处、量、空、发、分、为」等常见多音字使用单字全局替换**（如禁止写 `行: { say: 航, except: [...] }` 或 `调: { say: 条, except: [...] }`），因为任何漏写进 `except` 的词（如“先行”变成“先航”、“调岗”变成“条岗”、“权重”变成“权虫”）都会造成严重读音错误！必须**只按具体词组配置替换**（如 `已选行: 已选航`、`全部行: 全部航`、`多行: 多航`、`空白行: 空白航`、`各行: 各航`、`上一行: 上一航`、`行内: 航内`、`重算: 虫算`、`重置: 虫置`、`重复: 虫复`、`重新: 虫新`、`调平: 条平`、`调整: 条整`），并在生成 `output/script.json` 后逐句检查 `speech` 字段中每一个“行 / 重 / 调”的上下文读音是否完全正确！
5. **操作、视窗和旁白严格对齐（「所讲即所见：先入画再开讲、未讲完不切镜」，片头片尾极简，动作要写 `at`）**：
   - **片头与片尾必须极简（各一句话、4~5 秒以内）**：
     - 顶层 `intro.narration` **严格控制在 25 个汉字以内**，只用一句话点明本片主题（如「本视频演示待发布项目的发布操作。」），**严禁在片头罗列“包括第一步、第二步……请跟随画面操作”等冗长套话**；
     - 顶层 `outro.narration` **严格控制在 20 个汉字以内**，只用一句话干脆收束（如「以上就是发布项目的操作演示，感谢观看。」），**严禁在片尾重复罗列业务注意事项**。
   - **严禁念内部演练/测试话术**：即便采用 `ending.cancel` 不落库，旁白也必须按正常业务口径讲解（如「核对无误后点击确定即可正式发布；如暂不发布，可点击取消返回列表」），**严禁在旁白中写“演练阶段 / 本次只演示 / 不实际发布 / 不会产生任何业务数据变更”（`script.js` 会直接报错拒绝编译）**。
   - **所有关键动作必须写 `at`**：用 `at` 指定旁白念到哪个短语时做这一步（短语必须是旁白原文的子串）。**除场景开头的 `goto` / `wait` 外，每个动作（含用于把内容带入视窗的 `scroll` / `hover`）都要写 `at`**——不写就是立刻执行、与旁白脱钩。
   - **所讲内容必须在视窗内（通用视觉焦点法则，适用于一切页面与容器）**：
     - **先入画、再开讲（Reveal Before Narrate）**：无论旁白接下来要讲解的对象藏在何处——例如**长页面/长弹窗下半屏的区域**（如底部的预检结果区、统计面板、附加表单项）、**宽容器/宽表格横向滚动条外的区域**（如右侧的汇总列、对照列、操作列）、或**折叠面板/下拉菜单/子页签内部**——**都必须在该句旁白处配置 `- scroll: <目标元素定位>`、`- hover: <目标元素定位>` 或展开动作并配上 `at`**！执行器会自动驱动页面及任意内层可滚动容器的横向/纵向滚动条将该目标移至视窗中央舒适区，**严禁被讲解的内容还在屏幕外或未展开，旁白就已经开始空讲**！
     - **未讲完、不切镜（Hold Until Finished）**：只要旁白还在解释某个上下文内部的内容（无论是弹窗、抽屉、浮层、展开的详情区，还是刚刚滚入视窗的某块区域），**严禁提前关闭容器、切换页签、跳转路由或把滚动条移开**！若单个弹窗或区域要讲的设计点较多，必须拆成多个 `continue: true` 的连续场景，只在最后一个场景的 `ending` 中把关闭/离开动作的 `at` 锚定在收尾最后一句话上。
   - **`ending` 的动作尤其要写 `at`**：收尾旁白拼在整段末尾，收尾动作却接在基础动作之后，不写 `at` 必然抢在旁白之前提前关窗或提前提交。锚点取宣布该动作的那句话，通常是收尾旁白的最后一个分句（如 `at: 现在点击保存`、`at: 这里先收起菜单返回明细`）。没写的由工具默认锚到最后一个分句，但写准更好。
   - 动作执行后只剩 0.4 秒留白加 `hold`，要让「点完的结果」看清，就把该场景的 `hold` 调大（如 `hold: 2`）。`hold` 是**场景级**字段，写在 `ending.cancel` / `ending.submit` 里不生效（会直接报错）。
   - 完整写法照着 `script.yaml` 最后一个场景「修改订单备注」抄：清单关联、基础动作的 `at`、两种收尾、场景级 `hold` 都在那一段。
6. **定位**：优先 `{ role, name }`（来自无障碍结构），其次 `{ text }`，最后 `{ css }`；不稳定的写数组作为降级候选。两者的默认宽严相反：`{ text }` 默认**精确**匹配，`{ role, name }` 默认**模糊**，所以文案含百分比、数字或后缀时必须显式写 `exact: false`（例：`{ text: 必须等于 100%，不可保存, exact: false }`）。下拉选择用 `select`，附件/导入用 [文件动作](files.md)；有提前副作用的动作独立标记 `prepare`，不能借用最终保存权限。给手册看的步骤加 `label`；**对于关闭上一场景遗留抽屉（如 `.el-drawer__close-btn`）、按 `Tab` / `Escape` 失焦或无需单独占半页手册篇幅的二次确认框点击（如 `.el-message-box__btns .el-button--primary`），应显式加上 `doc: false`**，工具将跳过该动作的手册截图与步骤生成，避免手册出现“点击目标位置”或页数臃肿。
7. **断言**（真实提交的场景要断言成功提示或保存后的界面变化）：关键操作后用 `expect` 确认页面真的变化了（出现的文字、弹窗标题、地址）。用稳定的界面文字，不断言易变的条数或金额。弹窗和确认框的角色为 dialog。基础断言的位置由工具固定在收尾动作之前，**不能配置**；提交成功断言放在 ending.submit.expect，取消断言放在 ending.cancel.expect（如 hidden 证明弹窗已关闭）。`ending` 只能用在**只关联一个功能**的场景上，而且那个场景必须写 `feature`——没写 `feature` 时整块 `ending` 会被忽略，工具会直接报错。`ending.<模式>` 里只认 `narration` / `actions` / `expect` / `doc` 四个键，写别的会报错。正式手册会使用正式录制结果截图；演练素材独立保存，不会替代正式截图。
8. 每个场景写 `feature:` 关联功能 id。
9. **下列名字是工具内部字段，不要写进场景**：`writeMode`、`writeRequests`、`preparationRequests`、`expectAt`、`endExpect`、`cue`。提交授权由已确认的功能清单和 `ending` 派生，旁白锚点用 `at`，写了会直接报错。

## 配音前教学核对

在现有准备单或 `output/review-result.md` 中按「功能 → how 必讲点 → 场景 ID 与实际旁白 / 画面 → 完整、部分或缺失」核对；先补缺口，按已定阻塞策略只能文字讲解或跳过的如实记录。功能 ID 出现、演练通过都不等于知识讲全，无需新增脚本字段或逐项找用户确认。
通读相邻场景：先交代菜单入口；有个人范围与类型筛选时，先解释用户与数据的关系，再讲类型及操作。复杂交互用有差异的案例展示选择的影响，how 中已列的纠错路径须讲到修正与复核。检查异常解释是否有依据、符合业务限制；用条件语气讲未执行的结果，执行状态留内部核对。
