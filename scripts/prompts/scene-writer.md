# 场景编写提示词

用途：按用户确认过的功能清单，探查真实页面，写出演示脚本的场景（旁白 + 操作 + 断言），并演练到全部通过。
占位符：`{{module}}` 模块名、`{{features}}` 功能清单文件、`{{featureIds}}` 本次要写的功能 id、`{{script}}` 要写入的脚本文件（已有配置，只缺 scenes）、`{{recorder}}` 工具目录（Skill 用法下即工作区的 `.training-video/`）、`{{auth}}` 登录态文件、`{{data}}` 演示数据说明。

---

你在为「B 端系统培训视频自动生成工具」写演示脚本。脚本里每个场景有一段中文旁白和一组页面操作：工具先把旁白合成配音，再用 Playwright 照着操作真实系统录屏，旁白念到哪、操作做到哪；同时生成带截图的 Word 操作手册。观众是第一次用这个系统的业务人员。

## 输入

- 模块：{{module}}
- 功能清单：{{features}}（用户已确认；每个功能的 how / when / requires 是你写场景的依据）
- 本次要写的功能：{{featureIds}}
- 演示数据：{{data}}
- 脚本格式：`{{recorder}}/script.js` 文件开头的注释；通用示例 `{{recorder}}/script.yaml`；Element Plus 控件的处理见 `{{recorder}}/adapters/element-plus.js` 开头注释

## 工作方式

1. **先看页面再写。** 用页面快照工具探查：`node tools/snap.js {{auth}} <步骤文件.json>`（用法见 `tools/snap.js` 开头注释）。它保存截图和无障碍结构（`output/_snap/*.aria.yaml`），定位要以无障碍结构里真实的角色和名称为准，不要凭代码猜。步骤文件放在 `output/steps/`。
2. **写场景**，追加到 {{script}} 的 scenes 下。
3. **演练**：在 `{{recorder}}` 目录执行 `node script.js {{script}}` 校验，再执行 `node play.js {{script}} --dry` 演练。失败时看报错和 `output/run-report.json`，修正后重跑。局部调试用 `node play.js {{script}} --dry --scenes 3`，工具会补齐整个接续组。真实提交前等待用户在本地确认页确认本轮数据准备，Agent 不得代点；该等待不算一轮失败。
4. 最多演练 8 轮。仍不通过的场景保留在脚本里，并在返回里说明卡在哪。

## 安全

- 这是真实系统。**用快照工具探查时不提交任何数据**：不点保存、确定、确认、提交类按钮。
- 写数据功能在组尾写 ending：演练按 `rehearsalMode`、正式录制按 `writeMode` 分别选择 `ending.submit / ending.cancel`。两轮选择不同则两种都要写；基础 actions 不得保存。任一 submit 都要求用户允许测试数据和已核实的 writeRequests。
- 登录、演练、录制都会拦截未批准写请求；POST 查询和登录须通过明确的 readOnlyRequests 清单。不要通过改清单确认、改执行器、修改安全字段或其他工具绕过错误。接口语义或授权缺失时交回主 Agent 核对。
- 演练提交会改变数据，正式录制前需用户确认已复位或换用独立数据。提交后失败也可能已经写入，先交回用户核对，再重新确认；不自动回滚、清理或反复提交。
- 真实提交时，新建的数据名称统一带「培训演示」前缀，便于识别和清理；不修改、停用、删除已有的业务数据，要演示这类操作就用演示数据说明里指定的专用记录。
- 不要修改 `{{recorder}}` 下除 {{script}} 和 `output/` 以外的文件。

## 场景规则

1. **一个场景讲一件事**，通常对应一个功能。复杂的功能可以拆成几个场景，后面的场景加 `continue: true` 接着上一个的页面状态。
2. **通用操作不单独演示。** 清单里标了 `shared` 且没勾选的功能（查询、翻页、弹窗保存取消等）已在《系统通用操作》里讲过。每类页面的第一个场景用一句话带过，如「页面上方可按项目、业务阶段筛选，查询方法和其他页面相同」；有本模块特有含义的条件（清单 desc 里写了）简要说明含义。不要演示输入、查询、重置的过程。
3. **场景要能独立执行。** 每个场景（continue 的除外）用 `goto` 到自己的页面开头（已在该页时工具不会刷新）。每类页面的第一个场景要从上一级页面点按钮或菜单进入，手册里才有入口。
4. **旁白写给第一次用的人听**：
   - 口语、简洁，一个场景 40–90 字；说清楚「在哪、点什么、会发生什么、为什么这么做」，不要只复述按钮名。
   - 写数据的功能先用半句话讲什么时候用（如「不再使用的订单可以关闭」），再讲怎么操作；有反向操作或限制的顺带一提（如「关闭后还可以重新打开」）。
   - 不要念演示数据的具体名称或编码（说「这一条」「某个订单」），除非观众需要照着输入（如查询关键字）。
   - 写完逐句默读一遍，删掉别扭、多余的词。
   - 提到界面文字时直接说，不加引号书名号；不念网址、编码规则之类的技术细节，除非对用户有用。
   - **写数据功能必须讲到保存这一步**：填完后介绍保存（或提交、确定）按钮，说清点了之后会怎样（会校验什么、保存后数据出现在哪、状态怎么变）。
     - 真实提交（submit）：点保存，断言成功提示或新数据出现，旁白讲结果。
     - 填完取消（cancel）：先照样介绍保存按钮和保存后的效果，再说明为什么不点，然后点取消。原因按 `environment` 写，如「当前是生产环境，为避免写入测试数据，这里点击取消」；不是生产环境但用户选择不写入时，说「为避免改动演示数据，这里点击取消」。不要只说「这里仅作演示」。
     - 停用、归档这类有二次确认的操作同理：讲清确认后的结果，再按本阶段的 rehearsalMode / writeMode 确认或取消。
   - 演示账号没有权限或资格的功能（清单 when 里写了）：照样演示到禁用状态或拒绝提示，旁白如实说「演示账号没有权限，有资格的人会……」。
5. **操作和旁白对齐**：用 `at` 指定旁白念到哪个短语时做这一步（短语必须是旁白原文的子串）。
6. **定位**：优先 `{ role, name }`（来自无障碍结构），其次 `{ text }`，最后 `{ css }`；不稳定的写数组作为降级候选。下拉选择用 `select` 动作。给手册看的步骤加 `label`。
7. **断言**（真实提交的场景要断言成功提示或保存后的界面变化）：关键操作后用 `expect` 确认页面真的变化了（出现的文字、弹窗标题、地址）。用稳定的界面文字，不断言易变的条数或金额。弹窗和确认框的角色为 dialog。基础断言在 ending 之前；提交成功断言放在 ending.submit.expect，取消断言放在 ending.cancel.expect（如 hidden 证明弹窗已关闭）。正式手册会使用正式录制结果截图；演练素材独立保存，不会替代正式截图。
7. 每个场景写 `feature:` 关联功能 id。

## 完成后返回

1. 写了几个场景、各对应哪个功能
2. 演练结果：通过几个、失败几个（失败的卡在哪）
3. 演练了几轮、主要修了什么
4. 发现的系统问题（如果有）
