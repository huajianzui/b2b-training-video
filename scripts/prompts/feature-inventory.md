# 功能盘点提示词

用途：读业务系统代码，产出一个模块的功能清单（`<名字>.features.yaml`），交给用户在确认页勾选。
占位符：`{{module}}` 模块名、`{{system}}` 系统名、`{{code}}` 代码目录、`{{account}}` 演示账号、`{{script}}` 对应演示脚本文件名、`{{model}}` 模型名、`{{date}}` 日期、`{{out}}` 输出文件。

---

你在为「B 端系统培训视频自动生成工具」盘点功能。工具会按功能清单用 Playwright 操作真实系统录制培训视频（中文旁白），并生成 Word 操作手册。功能清单决定这个模块演示哪些功能，用户会在勾选页确认。清单要完整，但每一项都应该是值得在培训视频里讲的东西。

## 目标

- 系统：{{system}}
- 代码：{{code}}（只读这个目录）
- 模块：**{{module}}**，包括从它能进入的所有下级页面、弹窗、抽屉
- 演示账号：{{account}}

## 限制

- 只读代码。不修改文件、不启动服务、不操作浏览器。
- 只在 {{code}} 内搜索和读取。
- 唯一要写的文件：{{out}}

## 第 0 步：先建立页面基线

按规则逐页提功能之前，先机械地枚举模块的页面全集，作为后面自查的分母。**不要凭印象、也不要从页面截图上数页面**——快照只呈现当前账号、当前数据、当前分支渲染出的那一屏。

1. **从路由表枚举。** 在 {{code}} 里找前端路由定义。**要遍历整个路由目录，不只是主入口文件**——项目常按域拆分（例如 `router/systemRoutes.ts`、`xxxApplicationRoutes.ts` 与主 `router/index.ts` 并列），只读主入口会整体漏掉拆出去的模块；主入口通常 `import` 后展开这些子文件，要逐个追进去。若路由目录之外仍有 `path:` 定义（模块自行注册路由），一并纳入。逐条取出：路径、`name`、`component` 文件、`meta.permission`、`meta.title`。
2. **三种线索取并集。** 模块名、菜单标题、路径前缀都要用上，避免因命名不一致漏页。
3. **区分入口形态。** 标出哪些是独立页面（用户会停留、能做多种操作），哪些是弹窗 / 抽屉 / 表单页（按规则 2 不单列，但其中的功能归到发起它的页面）。**有独立路由、却只能从某个页面进去的**（申请记录、审批记录、明细子页），记下它的入口页面，并明确判断单列还是归并到入口页——不要因为它是「子页」就默认丢掉，也不要不加判断地一律单列。
4. **标出同一入口的多套实现。** 同一个路径按类型 / 状态渲染不同组件的（如项目类 / 非项目类明细），**每一套都要单独盘**。这是最容易整体漏掉的一类，规则 7 要求每个页面都列。
5. **建立基线并自查。** 得到「模块路由共 N 条 → 其中独立页面 M 个」作为分母。某条路由若没有对应功能、或某类页面拿不到源码，逐条写明原因，不要静默丢弃。

进入逐页提功能前，必须能回答：**模块共几条路由、计划纳入几个页面的功能清单、未纳入的是哪些及原因。**

## 判断规则

1. **一个功能 = 用户完成的一件事。** 同一个操作有多个入口（如明细页、维护页、申请记录页都能发起同一种申请）只算一项：挑用户最常用的入口作为它的 page，其他入口写进 desc（「也可以从 XX 发起」）。
2. **只为某个操作服务的页面不单列。** 点按钮后跳转、填完就回去的页面（申请表单页、某条申请的详情页）属于发起它的那个功能，不进 pages。pages 放用户会停留、在上面做多种操作的页面——包括从列表点进去的明细页、维护页。
3. **成对的开关合并。** 启用 / 停用、展开 / 收起这类写成一项（name 如「启用 / 停用任务」）。
4. **没资格 ≠ 演示不了。** 演示账号没有权限或业务资格，但入口看得见、点了会显示禁用状态或拒绝提示的，不写 blocked。在 when 里记录已核实的业务角色、可用条件及实际禁用 / 提示原文；账号限制用于内部准备，视频和手册按业务角色说明谁能办理、限制与后续路径，不讲演示账号配置。
5. **blocked 只用于什么都展示不出来的情况**：功能未接入、缺少必需文件且没有可演示的部分、代码 bug 导致功能不生效。缺文件但能演示一部分的（如能下载模板、能看导入窗口说明）不写 blocked，在 how 里写清能演示到哪一步。
6. **问题单独记录。** 分清已复现 bug、待核实阻塞、交互或视觉建议，写预期/实际、复现和代码/界面证据；不能只因查不到实现就定性业务 bug。普通建议留到集中交付。
7. **minor 标记**：操作一眼就会、不值得单独一个场景的（查看空状态的记录、和另一类页面完全相同的重复操作）写 minor: true。不同类型的页面（如项目类 / 非项目类明细）上同一个功能，**每个页面都要列**：用法有差异就在 desc 里写差异；没有差异的后一个标 minor，但不要省略——用户可能只想看其中一类页面的视频。
8. 在 how 中列出完成业务任务的必讲点：入口、条件 / 范围含义、关键选择和结果。复杂交互如批量录入，要覆盖有学习成本的加行、应用范围、空白保护、预校验及已核实的纠错路径；用能体现差异的连续案例串联，不把每个控件单列为功能。
9. 显示条件从模板的 v-if / disabled 和后端校验里找，写进 when。纯技术性的控件（刷新、分页）不列；查询的「重置」并进查询功能。
10. **通用操作标 shared。** 先找出系统的公共组件（如查询栏、表格、行操作菜单、表单弹窗的封装组件，被很多页面引用）。页面上直接由公共组件提供、用法和其他页面完全相同的操作，照样列出，但写 `shared: 查询`（或 表格 / 弹窗），由《系统通用操作》统一讲。判断看用法而不是看组件：查询条件里有本模块特有含义的（如业务阶段分售前、在建、售后），在 desc 里写清各选项含义，手册会列出；查询之外有特殊逻辑的（如联动、远程搜索人员），不标 shared。
11. 以用户任务确定粒度，不凑功能数量；再用**每页功能数**自查盘点粗细——平均每个页面 5–8 项，某个页面明显偏低说明该页盘得粗，回到第 0 步的页面基线复查是否漏页或漏功能。按小模块组织，便于全局和模块批量设置、少量重要例外单独确认。
12. 写功能追踪到实际请求，记录 `writeRequests: [{method, url}]`（包含来源和精确路径，可用单个 `{id}` 路径段）。GET 修改数据也属于写。不要猜接口；拿不准时说明待核实，不填通配规则。登录 POST、POST 查询等只读接口另外列给主 Agent，供脚本 `readOnlyRequests` 使用；读写共用路径不能整体标为只读。
13. 必填附件、上传即写入、导入预检留痕要列明。普通导入与首次初始化分别盘点，核实适用对象、是否允许重复及已完成后的维护路径；优先找系统模板下载入口及格式文档。缺文件先考虑经批准生成有效小样本，不直接判定无法演示。

## 输出格式（YAML）

```yaml
module: {{module}}
script: {{script}}
generatedBy: {{model}}
generatedAt: {{date}}
confirmedAt: ~                       # 固定写 ~，用户确认后回写
pages:
  - id: list                         # 短英文
    name: 订单列表
    entry: 左侧菜单「业务 › 订单管理」   # 用户怎么进到这个页面，用界面上看得到的文字
    route: /orders
    files: [views/order/OrderListView.vue]
features:
  - id: list.create                  # 页面id.动作，稳定
    page: list
    name: 新增订单
    kind: write                      # read 只读 | write 写数据
    desc: 这个功能是什么；其他入口
    how: 打算怎么演示（一两句，复杂交互分点）
    permission: order:manage         # 代码里的权限标识，没有就省略
    when: 显示 / 可用条件；演示账号没资格时会看到什么
    requires: 演示前提（要什么数据 / 文件）
    blocked: 演示不了的原因           # 只按规则 5、6 写
    minor: true                      # 只按规则 7 写
    shared: 查询                      # 只按规则 10 写
    source: views/order/OrderListView.vue:6
    writeRequests:                    # 仅写功能，必须来自真实业务代码
      - {method: POST, url: /api/orders}
```

不要写 include / writeMode / rehearsalMode / status（用户确认时回写）。不要自行填写 environment.testData，主 Agent 需先取得用户的环境选择。可以用 # 注释按页面分组。

系统改版后保留相同功能的稳定 ID，如实更新业务说明、权限、资格、前提和页面信息；不要为保留旧确认而沿用过期字段。主 Agent 用 `features.js merge` 合并后，新增、消失和同 ID 信息变化都需用户重新确认，已有环境和两轮收尾选择会保留。

## 完成后返回

1. 文件路径
2. **页面覆盖率：第 0 步枚举到 N 条路由 → 清单纳入 M 个页面；未纳入的是哪些及原因**
3. 页面数、功能数（write / blocked / minor / shared 各多少），以及平均每页功能数
4. 发现的 bug（文件、函数、现象）
5. 最不确定的 3–5 个判断及原因
6. 核实的写接口和只读 POST / WebSocket 接口；尚不能区分查询与修改的共用接口
