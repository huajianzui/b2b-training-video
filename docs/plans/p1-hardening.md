## 已实施的写入与演练契约

用户选择：演练也单独确认；在已确认的测试环境可真实提交，确定与取消的结果需分别验证。保留正式录制逐功能的 `writeMode`，新增逐写功能的 `rehearsalMode`（cancel / submit，未选择时待确认），不自动选择演练取消或提交。

1. 先确认当前 URL、环境名称和能否写测试数据。`environment.testData` 不是按“测试”字样猜测，必须来自用户选择。任何 submit 都要求它为 true，并要求清单已经确认。草稿改变 include / 两种收尾选择后清除旧确认。未声明演练方式的旧写脚本给出迁移提示。
2. 写功能必须在场景组最后提供对应 `ending`；`continue` 分段可以保留表单，但组尾必须收尾。取消与提交分别编译，不用 dry 标志推断同一组动作安全。基础动作始终不得提交。
3. 写功能声明 `writeRequests: [{method, url}]`；脚本声明 `readOnlyRequests: [{method, url}]`（含登录和 POST 查询，须核对业务代码）。精确方法、来源、路径和查询参数匹配，可用 `{id}` 表示单个动态路径段；不允许通配域名或任意路径。运行时检查每一跳 HTTP 请求，未声明的写方法和已知 GET 写路径均受限，后者的 HEAD 也禁止默认放行。每轮仅在获准功能的 submit 收尾内开放该功能的接口。拦截写请求必须生成失败报告，不能假装通过。关闭 service worker；WebSocket 仅放行声明为只读的连接，不开放业务写通道。
4. 每个会真实提交的阶段执行前，通过现有本地确认页等待用户确认本轮脚本、环境与数据已准备好。等待文件带随机 runId、进程号和输入摘要；确认请求携带当前 runId/input/stage，并受同源、令牌保护。演练提交后，正式录制单独停下来确认已复位或换好独立数据。取消或进程退出不继续运行；旧确认不能批准下一轮。
5. 正式手册从正式录制截图生成，保证与正式收尾一致；`--dry` 的手册采用演练动作并明确标记演练用途。每份素材绑定当前编译输入；正式手册不能借用演练取消截图。流水线阶段和续跑来源记录随之调整。
6. 直接调用 play.js 也重新校验 YAML，并执行相同确认和路由保护。TTS manifest 记录 voice / rate / 每场景 speech，录制拒绝旧或不匹配的旁白；不通过直接调用绕过流水线检查。

验收：用户未确认不发生写入；testData false、草稿、缺 ending、基础动作保存、未声明的 POST/PUT/DELETE 都失败；正常 POST 查询和登录可用；演练 submit、正式 cancel 和演练 cancel、正式 submit 两种组合独立；两阶段都 submit 时，第二次数据确认前后台计数保持一次；过期确认和跨站确认失败；真实浏览器、截图、正式录制、Word 与续跑均覆盖。

限制：客户端保护依赖已核对的接口语义，不能推断业务系统把未知 GET 当写操作；不自动修改业务数据或实现系统专属复位逻辑，复位/独立数据由用户确认。外部 TTS 服务可用性和真实业务系统权限由集成验证覆盖。
