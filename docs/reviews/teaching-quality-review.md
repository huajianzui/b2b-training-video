# 培训内容质量复审与规则对照

日期：2026-10-14。状态：四份脚本对照完成；用户随后批准教学指令小修，实施与回归见末节。当前成品的教学缺陷尚未修复。接续[制作体验复审](experience-revision-review.md)；对照阶段只做内容研究与报告，后续也不操作业务系统、不生成语音或重录视频。

## 已确认的成品问题

用户提供优化前的视频后，对照相关画面、旁白、执行脚本和当前业务实现，确认工程验收与培训内容验收之间存在缺口。

| 检查项 | 优化前视频 | 本轮改版后的成品 | 判断 |
|---|---|---|---|
| 菜单入口 | 约 00:18–00:28 展示项目管理 → 任务库管理 | 直接进入列表 | 已有场景规则未落实 |
| 个人范围含义 | 介绍标签，但基本是同义重复 | 仍未解释实际业务关系 | 业务梳理与讲解不足；旧版也不是完美基线 |
| 范围与类型 | 先个人范围，再类型 | 先类型，再个人范围 | 教学层级不符合用户先找与自己相关数据的任务；类型数量随范围变化 |
| 项目批量录入 | 约 05:30–08:13，五段，真实画面含多行、覆盖范围、仅填空白和纠错 | 约 26 秒，只填写一行 | 复杂功能教学缩水；功能清单中 how 已要求的环节没有兑现 |

上一轮 32 项功能关联 34 个场景、132 项测试通过，证明了批准范围下的执行与对应工程回归；不能据此证明受众理解了功能。入口、复杂交互等已有要求也未转化为有效的内容验收。当前成品的教学完整性不通过；上一轮的运行、数据与媒体证据仍保留原适用范围。

## 规则差异核查

对比最早发布版 `5b42b2f`、制作体验改版前 `2a51e4c` 与本轮对照基线 `82b8adc`：

- 每场景 40–90 字、复杂功能可拆连续场景、首场景从上一级菜单进入，早已存在。不能把新版的一功能一小段视为新增硬性限制。
- 本次改版保留了批量加行、批量设置和预校验的盘点要求；新清单确有这些 how，但实际场景不足。
- 本次新增按业务顺序通读、自然过渡，以及取消时说明正常办理路径、制作约束留内部报告。是否有效需要检查实际产物，不能因提示词出现要求就认定已解决。
- 旧目录留存的提示词可辅助比对，但不能保证还原当时所有用户消息、模型参数和迭代过程。
- 对照基线有一处受众口径冲突：当时的[功能盘点规则](../../scripts/prompts/feature-inventory.md#判断规则)要求视频讲“演示账号没有权限”，而[场景规则](../../scripts/prompts/scene-writer.md#场景规则)要求按业务角色解释、不对观众讲演示账号配置。本实验账号具备资格，不会触发该冲突，因此不把它算成样本失败，也不能用实验通过证明此问题不存在。后续已在原条目统一，见末节。

已证实的直接问题是 Agent 场景编写与验收不足。工程规则变多是否影响模型注意力、模型差异是否主导质量，尚无足够证据。

## 固定事实的小范围对照

实验在生成前固定方法、业务事实与 24 项内容检查点。旧组使用 `5b42b2f` 的入口、盘点与场景提示词；新组使用 `82b8adc` 的对应文件及其引用的集中准备文档。每组两份，使用同一当前会话模型及默认继承的推理配置、独立新上下文；不提供原视频、缺陷结论或另一组结果。

三章固定为入口与个人范围、项目任务在线批量录入、标准工作量变更申请。两组共享已核实的当前业务事实、必讲内容、实际收尾和文稿格式；不限制总场景数或总字数。所有样本保留，不从重复中挑选赢家。

检查项覆盖：入口与数据范围 5 项、批量交互 12 项、申请流程 7 项。逐项区分完整、部分、缺失与错误，引用实际旁白/镜头；另外评价教学顺序、承接、指代与镜头一致、业务受众视角、解释深度与负担，主观分数不当作模型客观排名。

本地完整证据位于会话工作区 `work/teaching-quality-study/`，包含方法、共同任务、两版规则快照、输入摘要、四份原始脚本及核对记录。业务样本与原视频不加入 Skill 源码。

事实预检曾发现首包把“复制单行”错误概括为“复制当前行”；当前源码实际是“复制上一行到当前行”，不增加行数。这是本轮事实整理错误，尚未证明旧视频当时的控件行为不同。首轮两个样本在完成前停止、另两个未启动；原输入保留并排除评分。纠正共同事实后，四份有效样本统一使用 v2 输入和全新上下文，排除依据在看最终样本表现前确定。

## 归因与修正建议

1. **不能认定“Skill 整体优化坏了”或“当前模型不会写”。** 在事实和必讲内容明确、新上下文条件下，旧、新规则各两稿均能写全复杂教学。它反对“新规则必然只能浅讲”的解释，不证明新 Skill 完美。
2. **有直接证据的问题是内容生产和验收没有兑现教学要求。** 成片漏入口、how 已列批量环节却未展示，是实际失败；执行覆盖与媒体解码检查未检出。应优先修复这条链，而不是换模型后假定问题消失。
3. **规则仍有具体缺口，但不宜整体回退。** 统一权限旁白的冲突条目；保留新版正常提交/审批讲解及制作说明隔离的收益。审批、取消口径应按业务选择表达，不把“本次不做”变成片尾口头说明。
4. **在原有 how 和场景审稿处补可核对的教学依据。** 每项复杂功能列少量必讲点，对应到实际旁白/镜头；功能 ID 出现不算知识点覆盖。业务动作按一个连续案例组织，必要时拆场景，不机械地每个控件一个小段。不要另造一套 YAML 权限字段、确认流程或固定场景数限制。
5. **分开验收三件事。** 工程是否可执行、知识是否讲全、用户是否容易跟着学。今后修改编写规则时，复用本次三个小片段检查入口/复杂交互/条件审批，并通读相邻旁白；只跑工程测试或搜到几个关键词都不算内容回归。

本地另交付 `editorial-example.md`：将同样三章整理为 14 场景、1195 个旁白字符，用一批有差异的任务连续展示，不再为了教清空按钮而重填整个案例。它是看到实验结果后的编辑示例，不计入对照，也未证明 14 场景是最优值。后续若配音窗口不足，应拆连续场景而非删知识或加快语音。真实定位、配音、录制和用户学习效果均未验证。

## 边界与后续判定

这是固定事实条件下的脚本生成实验。事实包明确列出必讲知识，不能代表 Agent 从零盘点是否会发现这些知识；新上下文也没有复现长会话、工具失败或时间压力。没有测试实际口播节奏、镜头停留和操作时序。两次重复不能给出统计显著性，没有调用 Gemini 或 Grok，不能据此排名模型。

修正方向先保留工程防护，以旧成品中已验证的教学结构作为局部基线；在现有 how 和场景审稿处核对必讲知识，而不是继续增加功能计数。具体规则修改应依据本轮结果确定，不靠继续堆叠“自然、完整、清楚”等泛化要求。

## 教学指令小修与回归

用户补充确认 OVM 初始化“一库一次”，并授权修改上述小修项。范围：入口和两个现有提示词、安装回归及本报告；不改执行器、脚本字段、确认流程或业务代码。以下是对照实验之后的修订，不反向修改原始样本或评分。

- 权限口径：盘点的 when 保存真实限制供准备使用，视频和手册讲已核实的业务角色与办理条件，统一两处冲突要求。
- 教学核对：复用 how 和既有准备单 / 问题报告，把必讲点对应到实际旁白、画面与场景；先审稿再配音，交付再核对实际成片。按连续业务案例组织，不把功能 ID 或工程测试当教学通过。
- 异常解释：讲现象、证据支持的原因、符合业务规则的处理与验证。输入错误可以纠正；一次性操作或状态不适用须解释适用范围，不指导改编码或清记录绕过。原因未知时保留未知，不据报错推断历史。

OVM 依据：用户本轮确认优先；`TaskLibraryInitialImportService.preview` 的 `FILE_ALREADY_IMPORTED`（第 69–86 行）、`TaskLibraryInitialImportCommitService.commit` 的重复成功记录拒绝（第 93–99 行），以及 `TaskLibraryInitialImportAssembler.validateLibraryScope` 的库范围、编码检查（第 453 行起）。项目库还检查来源项目和任务编码；不能把各类型都解释成同一个实现条件。页面第 13 行区分首次初始化与日常导入，冻结契约第 8–17 行区分首次建库和现有库内操作。

因此，先前答复中的“调整编码后重新导入”不适用于已经初始化的同一个库。正确教学是说明已完成首次建库、无需也不能再次初始化，后续从已有库维护；另一个尚未初始化的新库才按其适用资料、预检、核对、确认与结果检查流程办理。不能保证新库必然预检通过。该 OVM 事实保留在回归案例，通用 Skill 不硬编码所有系统初始化均为一次。

回归输入保存在 [teaching-cases.md](../../scripts/tests/teaching-cases.md)，使用隔离上下文完成短稿，评审者核对原文，不能只读作者的“通过”判断。生成前固定检查如下：
